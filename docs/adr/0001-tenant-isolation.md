# ADR 0001 · 用 PostgreSQL 行级安全做租户隔离

- 状态：已采纳（M0）
- 日期：2026-10-15

## 决定

1. 应用运行时以 `hb_app` 角色连接数据库。它不是任何表的所有者，没有 SUPERUSER 和 BYPASSRLS，所以它发出的每条查询都受行级安全约束。迁移用所有者账号执行。
2. 每个请求在一个事务里由 `withTenant`（`apps/server/src/db/database.ts`）写入租户上下文：`app.user_id`、`app.role`、`app.operator_id`、`app.org_id`。上下文只在事务内有效，连接回到连接池后自动清空。
3. 没有上下文时，所有策略都不放行。
4. 会话表和密码哈希列对 `hb_app` 不可见，登录和会话校验只能通过几个 SECURITY DEFINER 函数完成，令牌只存 SHA-256。
5. 客户所属机构通过外键跟着健管师走（`on update cascade`），健管师调机构时客户一并转移。
6. 跨租户访问一律返回“不存在”。

## 行级安全防什么、不防什么

- **防**：业务代码写错查询，比如忘了加条件、拼错了 id。即使绕过仓储层直接查询，也拿不到别的租户的数据。
- **不防**：应用本身被攻破。`hb_app` 可以自己调用 `set_config` 改写上下文，也可以调用登录函数。所以：
  - 代码规范禁止在 `db/database.ts` 以外出现 `set_config`；
  - 原始 SQL 只允许出现在 `db/` 目录和 `auth/auth.repository.ts`，业务代码只用查询构造器；
  - 所有参数都走参数化查询。

## 已知取舍

- 登录频率限制是单实例内存版，按邮箱锁定可能被他人利用来暂时锁住某个账号（15 分钟）。多实例部署时改用 Redis，并考虑改成逐步延迟而不是锁定。
- 会话绝对有效期 14 天，空闲 3 天失效。
- `trust proxy` 设为 1 层，按 Railway 前面一层边缘代理配置；换部署平台时要重新确认。
- 应用角色是整个数据库集群共享的。生产库不要和其他环境共用集群。

## 待办（M6 客户账号上线时）

- `llm_usage` 目前对运营商和平台逐条可见。客户账号（AI 健康伴侣）上线后，客户的调用记录会暴露其使用频率，违反“运营商和平台看不到客户明细”。届时客户行对运营商和平台只提供汇总视图，或对 user_id 去标识化。
- `llm_usage` 没有 org_id，机构管理员暂时看不到本机构的用量，M7 做运营看板时补上。
