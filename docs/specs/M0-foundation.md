# M0 · 地基 需求规格

> 状态：**待 Adrain 确认**（见第九节“待确认问题”）
> 依据：[功能清单第三版](../feature-list.md)、[路线图](../roadmap.md)

## 一、目标

搭好后面所有里程碑共用的底座。M0 做完后，你能打开一个预览网址，用测试账号登录，看到一个空的健管师工作台。后台已经具备以下能力：
- 多租户隔离
- 调用 Claude
- 自动测试和检查

M0 本身没有业务功能。它的价值在于让后面每个里程碑都能直接在上面开发，不用返工。

## 二、范围

**包含**
1. 单仓库、代码规范、持续集成（GitHub Actions）
2. 五级账号和租户数据模型，以及数据库层面的租户隔离
3. 健管师和管理员的登录、退出、会话管理
4. 大模型网关（Claude API）
5. 合成测试数据生成器
6. 设计规范（颜色、字体、间距、组件基础），支持按运营商换品牌色
7. 工作台空壳：三栏布局骨架，登录后可见
8. 预览环境：每次合并到 main 自动部署

**不包含**（放到后续里程碑）
- 对话、技能、专家等任何 AI 功能（M1 起）
- 客户端和客户登录（M6）
- 平台和运营商后台页面（M7；M0 只做数据模型和接口层权限）

## 三、仓库结构

```
apps/
  workbench/     健管师工作台（React + Vite + TypeScript）
  server/        后端 API（NestJS + TypeScript）
  admin/         平台和运营商后台（M7 再建，M0 只占位）
  client/        客户端（M6 再建，M0 只占位）
packages/
  shared/        共享类型和接口契约（zod）、禁用词表
  ai-engine/     大模型网关（M0），以后加主智能体、技能和专家引擎
  ui/            设计规范和基础组件
  experts/       （M3）
  skills/        （M1）
scripts/seed/    合成数据生成器
docs/
```

## 四、账号与租户模型

### 4.1 五级账号

| 层级 | 谁 | 能看到什么 |
|---|---|---|
| 平台 | 我方管理员 | 全部运营商的统计数据；默认看不到客户明细 |
| 运营商 | 协会管理员 | 本协会的健管师、机构和统计数据；看不到客户明细 |
| 机构 | 健管机构管理员（可选层级） | 本机构的健管师和客户 |
| 健管师 | 健管师本人 | 自己服务的客户的全部数据 |
| 客户 | 终端客户 | 只能看到自己的数据（M6 启用） |

### 4.2 数据归属规则
- 每条业务数据都带 `operator_id`（属于哪个协会）。机构数据还带 `org_id`。客户数据带 `manager_id`，表示服务该客户的健管师。
- 隔离在数据库层强制：PostgreSQL 行级安全（RLS），每个请求开始时设置当前用户的租户上下文，策略只放行该上下文可见的行。
- 后端代码只能通过“带租户上下文的仓储层”访问数据。直接写原始 SQL 会被代码规范检查拦下。
- 跨租户访问一律返回“不存在”，不提示“无权限”，避免泄露数据是否存在。

### 4.3 登录
- M0 用邮箱加密码登录。密码用 argon2 哈希，登录有频率限制。
- 会话放在 httpOnly Cookie 里，有效期和刷新机制在实现时定。
- 预置一个平台管理员账号，由部署时的环境变量初始化，不写进代码。

## 五、大模型网关

所有 Claude 调用都经过 `packages/ai-engine` 的网关，业务代码不直接调用 SDK。

- **SDK**：官方 `@anthropic-ai/sdk`。
- **模型**：默认 `claude-opus-5-5`（Claude Opus 5.5），开启自适应思考。按用途（路由）配置模型和思考强度（effort），以后可以给某个用途换模型，不用改业务代码。
- **流式输出**：默认流式，前端能实时看到生成过程（M1 的执行步骤展示依赖这一点）。
- **拒答兜底**：开启服务端 fallback，模型拒答时自动换模型重试，并正确处理 `refusal` 停止原因。
- **计量**：记录每次调用的租户、健管师、用途、输入输出 token 数和费用估算，供以后计费和成本分析。
- **日志不含健康数据**：只记录用途、耗时、token 数和错误类型，不记录提示词和回答原文。需要排查问题时使用单独的、默认关闭的调试开关。
- **测试替身**：单元测试和持续集成里用模拟网关，不调用真实 API，也不花钱。真实调用只在评测（`pnpm eval`）里进行。
- **密钥**：Claude API 密钥只放在部署平台的密钥设置里，代码和仓库里都没有。

## 六、合成测试数据

`scripts/seed` 生成一套虚拟数据：
- 1个平台、2个运营商（协会A、协会B），每个协会1个机构和3名健管师，每名健管师10位客户
- 每位客户有基本信息、2到3份体检报告（结构化指标，M2 再补充 PDF 和图片样本）、30天监测数据
- 姓名、电话等全部是假数据，明确标注“测试数据”
- 两个协会的数据用来测试租户隔离

## 七、设计规范与工作台空壳

- 设计规范定义颜色、字体、间距、圆角和阴影，支持浅色和深色模式。品牌主色可以按运营商替换（M7 的品牌定制依赖这一点）。
- 中文界面字体优先使用系统中文字体，数字和英文用无衬线字体。
- 工作台空壳：左侧栏（新建任务、任务列表、技能、专家中心、自动化、设置的占位）、中间对话区占位、右侧结果区（可收起）。电脑和手机都能正常显示。
- 视觉风格参照 WorkBuddy 的交互布局，配色、图标、插画自己设计。

## 八、验收标准

1. 在预览网址用测试健管师账号登录，看到三栏工作台空壳；退出后无法访问。
2. 协会A的健管师无法读取协会B的任何数据：每个接口都有自动化测试，而且数据库层也拦得住（绕过仓储层直接查询同样拿不到）。
3. 运营商和平台管理员账号查不到客户明细。
4. 网关能流式调用 Claude 并记录用量；日志里搜不到提示词或回答原文。
5. 持续集成在每个 PR 上运行 lint、类型检查、单元测试和构建，全部通过才能合并。
6. 合并到 main 后预览环境自动更新。
7. `pnpm seed` 一条命令生成全部测试数据。
8. 工作台空壳在手机宽度下没有横向滚动，布局正常。

## 九、待确认问题

1. **预览环境用哪家**：建议用 Railway。前端、后端、PostgreSQL 和 Redis 都能放在一处，配置最少，按用量付费。正式环境以后再定，可以迁到 AWS 等大厂。也可以直接告诉我你们已经在用的云服务商。
2. **界面语言**：只做简体中文，还是同时支持繁体中文？海外华人里用繁体的不少（比如港台、东南亚和北美的部分社区）。建议架构上从一开始就支持多语言，先做简体，繁体以后补。
3. **登录方式**：M0 先做邮箱加密码。是否需要手机号验证码或微信登录？如果需要，可以放到 M7 或之后。
4. **产品名称**：界面上显示“健管AI助手”还是“Health Buddy”，或者两个都用（比如中文名“健管AI助手”，英文名“Health Buddy”）？
5. **模型成本**：网关默认所有用途都用 Claude Opus 5.5。AI 健康伴侣的日常陪聊调用量会很大，以后是否换成更便宜的型号，由你决定。网关支持按用途切换，到 M6 时再定也可以。
